# Entity Expansion Roadmap

Документ фиксирует рабочую приоритизацию сущностей для расширения синтетического генератора и будущей модели PII Detection.

Исходные вводные:

- текущий синтетический пайплайн уже поддерживает 9 сущностей;
- в `entities.numbers` описано около 90+ потенциальных сущностей для PII Detector;
- в реальном датасете из 2ch/Двача размечены 500 текстов с реальными PII-кандидатами;
- часть сущностей важна именно для PsyTechLab, где цель шире: найти любые данные, по которым можно идентифицировать автора или связаться с ним;
- для бизнес-задачи PII Detection важнее сначала покрыть частые и универсальные персональные данные, которые бигтехам нужно маскировать в текстовых данных.

## Критерии приоритизации

Сущность получает высокий приоритет, если она:

1. часто встречается в реальном датасете;
2. является прямым идентификатором человека или контактом;
3. важна для маскирования данных в бизнес-сценариях;
4. относительно понятно генерируется синтетически;
5. не создает слишком много коллизий с уже существующими regex-сущностями;
6. помогает покрыть разные типы PII: документы, контакты, аккаунты, финансы, адреса, биографические и чувствительные атрибуты.

## Stage 3: PsyTechLab-specific и редкие сущности

Эти сущности могут быть важны для PsyTechLab, потому что помогают находить любые способы идентификации или связи с человеком, но для первого business-oriented PII baseline они не критичны.

| Группа | Примеры | Почему позже |
|---|---|---|
| Игровые платформы | `STEAM`, `EPIC_GAMES`, `BATTLETAG`, `PSN`, `XBOX`, `ROBLOX`, `GENSHIN_UID` | Полезны для PsyTechLab/contactability, но в бизнес PII masking обычно ниже приоритет. |
| Редкие мессенджеры | `TELEGUARD`, `SIGNAL`, `VIBER`, `MAX`, `SKYPE` | Нужны для полного покрытия контактов, но можно добавить после популярных соцсетей. |
| Семейные документы | `MARRIAGE_CERTIFICATE`, `BIRTH_CERTIFICATE` | Документы важны, но редко встречаются в пользовательских текстах. |
| Редкие личные документы | `MILITARY_ID`, `REFUGEE_ID`, `RESIDENCE_PERMIT`, `COMBAT_VETERAN_ID`, `LARGE_FAMILY_ID`, `SEAFARER_ID`, `WORK_BOOK` | Высокая специфичность, меньше пользы для первого baseline. |
| Судебные идентификаторы | `ENFORCEMENT_PROCEDURE`, `ARBITRATION_CASE`, `COURT_CASE_NUMBER`, `COURT_ORDER_NUMBER`, `COURT_CASE_SOJ_NUMBER` | Важны для отдельных доменов, но лучше после core PII. |
| Документы об образовании | `EDUCATION_DOC` | Не путать с `EDUCATION`: это номера дипломов/аттестатов, а не факт образования. |
| Электронные кошельки | `YMONEY`, `WEBMONEY_PURSE` | Финансовые, но более нишевые, чем карта/счет. |

## Замечания по canonical labels

Есть несколько расхождений между `entities.numbers`, YAML-конфигами и реальным датасетом. Перед генерацией пулов нужно зафиксировать canonical labels.

| Real / желаемый label | Detector config label | Комментарий |
|---|---|---|
| `LICENSE_PLATE` | `LICENSE_PLATE_RU` | Лучше использовать короткий model label `LICENSE_PLATE`, а regex-конфиг оставить как источник. |
| `TWITTER` | `TWITTER_X` | Нужно выбрать один canonical label. Для модели лучше `TWITTER_X`, если хотим явно учитывать X. |
| `HEALTH` | нет единого regex label | В Numbers это состояние здоровья/диагнозы/аллергии; для модели можно временно объединить в `HEALTH`. |
| `EDUCATION` | нет равного regex label | Не путать с `EDUCATION_DOC`: `EDUCATION` — факт/уровень/место образования, `EDUCATION_DOC` — номер документа. |
| `OMS_DMS` | `OMS` + ДМС как NER | Для Stage 1 предлагается начать с `OMS`, ДМС можно добавить позже или объединить в `MEDICAL_POLICY`. |
| `AUTHOR_LINKS` | нет отдельного label | Вероятно, это meta/source field, а не отдельная PII-сущность для модели. |
| `OTHER_CAREER_PLATFORM` | нет отдельного стабильного label | Лучше вводить после `HH`, `LINKEDIN`, `HABR_CAREER`, `SUPERJOB`, `AVITO`. |

## Практический порядок работы

1. Добавить генерацию пулов для новых Stage 1 сущностей.
2. Для каждой сущности собрать небольшой test pool и вручную просмотреть качество.
3. Добрать финальные пулы и перенести их в `data/entities_pool` синтезатора.
4. Сгенерировать синтетический датасет с 30 сущностями.
5. Обучить baseline-модель (`BERT` или `GLiNER`).
6. Протестировать на real dataset из Label Studio.
7. По ошибкам решить, какие Stage 2/3 сущности добавлять следующими.

## Не делаем на первом этапе

- Не пытаемся сразу покрыть все 90+ сущностей.
- Не усложняем preprocessing/postprocessing LLM-фильтрами до первого baseline eval.
- Не решаем все regex-коллизии заранее; сначала берем сущности с максимальной практической пользой.
- Не смешиваем `EDUCATION` и `EDUCATION_DOC`, `HEALTH` и медицинские документы, social usernames и platform-specific profile links без явного mapping.
